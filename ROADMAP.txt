            (280) lobs 110 over a 4.5m blast, four shells at a time.
            Their paths forced a real improvement. Delivery parameters lived
            in the delivery ASSET, so a Wildfire path could not widen its cone
            and a Storm path could not grow its chain - the two things those
            fantasies are entirely about. WeaponStats now carries
            ConeHalfAngle, ChainBounces, ChainHopRange, ChainDamagePerHop,
            BlastRadius and Range, all -1 meaning "use the delivery's own
            value". The asset says where a weapon starts, the path says where
            it goes.
            Six more fields, and again every one is a plain override of a
            parameter that already existed rather than a new mechanic - the
            same pattern as the shotgun/rifle/sniper batch. See debt 17: the
            vocabulary keeps growing in the least interesting direction, which
            is a strong hint about what the eventual rework should target.
            It paid off immediately: Bombardier's Cluster tier is just
            pelletCount = 3, because ProjectileDelivery already loops the
            pellet count. Three shells a trigger pull cost no code at all.
            NOT PLAY-TESTED, and these are the first things ever to run the
            three new modes - expect mode bugs before balance problems.
            Storm's T5 gains 10% per hop over eight hops, which is the same
            compounding shape as sniper overpenetration and the same first
            candidate for tuning.
2026-09-09  Horde pathing fixed. Zombies steered in a straight line at the
            player with no awareness of geometry, so anything behind a cover
            block pressed into it forever, held there by its own
            CharacterController. Replaced with a shared FlowField: one
            Dijkstra sweep over a 90x90 grid at 1m cells - the grid barricades
            already snap to - rebuilt only when the player crosses into
            another cell or the barricades change. Each zombie reads the cell
            it stands in, which is one array lookup and cheaper than the
            normalize it replaced.
            NOT NavMesh, deliberately: the scene is builder-generated so
            baking is awkward, runtime barricades would each need a carving
            obstacle, NavMeshAgent wants to own transform movement and would
            fight the CharacterController and the knockback impulse, and sixty
            agents of NavMesh avoidance is heavier than a field lookup.
            Barricades are stamped EXPENSIVE rather than impassable, at cost
            30. Impassable would have made the horde walk around a wall
            instead of clawing through it, which quietly deletes the
            fortification hook. At this cost a short wall is a detour and a
            long one is a door. That number is the first thing to tune:
            zombies pressing on a wall they could route around means it is too
            low, absurd detours around two panels means too high.
            Within 3 metres zombies revert to a straight line - the grid is
            coarse next to the player, the attack range wants precision, and
            any failure of the field degrades to the old behaviour rather than
            to standing still.
            Three defects caught in review, two of them the quiet kind. The
            bake used CheckBox, which does not care what it hits: the player
            is standing on the grid when it bakes, so their spawn cell would
            have been permanently impassable for the whole run. The heap was
            sized at 4x the cell count when lazy deletion makes the true bound
            8x, so a full heap would have silently dropped pushes and produced
            a quietly WRONG field rather than a crash. And queries ran before
            Physics.SyncTransforms, on the frame the scene loads.
2026-09-09  Firing modes built, closing debt 19 and unblocking the six
            remaining weapons. WeaponDelivery is a ScriptableObject with one
            method rather than an enum with a branch per mode - the same
            reasoning that turned deployables into definitions and got mod
            cores deleted. An enum would have meant every new weapon kind
            editing the same file, which is the debt this project keeps
            paying off.
            The split is the part worth remembering: Weapon keeps everything
            true of every firearm (ammo, rate, which hand fired, whether the
            shot crit, which direction the ultimate picked, plus focus,
            executions and kill credit), and a delivery owns only how the shot
            travels. Everything a delivery needs arrives in a ShotContext
            rather than being reached for through the weapon, so a delivery
            can be read without reading Weapon.cs - and akimbo, the ultimate,
            crits and focus work with every mode for free.
            Four modes: Hitscan (a straight port, no behaviour change),
            Cone (flamethrower - continuous fire modelled as a very high rate
            of very small shots, so a fuel tank is a magazine and a tick of
            flame is a round, rather than a second firing lifecycle running
            beside the first), Chain (Tesla - first link is a real raycast so
            walls block it and aiming matters, every hop after is a search
            because an arc refusing to bend around a corpse would read as
            broken), and Projectile (grenade and nail, spherecast swept so a
            fast round cannot tunnel, statically pooled like EnemyProjectile).
            Blast is back from the marks path, better: enemies from the horde
            list, plus a small physics query purely to chain explosive
            barrels, and it touches neither the player nor their barricades.
            NONE OF THE THREE NEW MODES HAS EVER RUN. No weapon references
            them yet, so the first weapon built on each mode is really a test
            of that mode.
            One deliberate behaviour change: auto-aimed shots (the ultimate,
            Split Focus) used to fire exactly one pellet and now fire the
            weapon's full count. No live weapon hits this - only the pistol
            has either - but the old behaviour was wrong.
2026-09-09  Design direction changed, and this is the third time the upgrade
            structure has moved, so the reasoning matters more than the result.
            Three paths per weapon on four weapons meant 60 tiers, and the
            5-3-0 rule needed all three to exist before any of them was a
            choice. Settled instead on TEN weapons with ONE path each: the run
            decides which weapon to pour gold into, and with a maxed path at
            3360 against 6580 income it can only ever afford one. The player
            handles all ten guns every run; exactly one of them feels
            powerful. Cost is the same 50 tiers, but the variety now comes
            from the arsenal rather than from branching inside one gun.
            5-3-0 survives untouched in UpgradeManager and simply goes inert -
            a single open path can never breach it - so a weapon can be given
            three paths later as data plus a wider panel.
2026-09-09  Loadout reworked, closing debt 16. WeaponLoadout now holds a
            catalogue (everything the Armory sells) and a carried array (what
            the run holds), replacing a fixed slots[4] with a parallel
            unlocked[4] that could not express ten. Carry capacity is 10,
            mapped to the number row 1-9 then 0. Weapon prices moved onto
            WeaponDefinition, so ArmoryPrices is down to a single field and a
            tenth weapon is an asset plus a catalogue entry - no constant, no
            branch, no button. The shop builds its weapon list in a loop and
            sizes its own card to fit it.
2026-09-09  Three more upgrade paths, all hitscan so none needed new firing
            code. Shotgun "Streetsweeper" ends as a 12-pellet 200 RPM wall
            that feeds itself a shell per kill. Assault rifle "Marksman"
            stacks damage for consecutive hits on the SAME target and tightens
            its spread the longer you hold - the deliberate mirror of the
            pistol's fan, both driven off one triggerHeat value in opposite
            directions. Sniper "Executioner" makes each pierced body make the
            round stronger rather than weaker, and executes anything under 30%
            health whatever its maximum, which is the answer to the boss.
            Numbers to watch: overpenetration compounds to roughly 9x on the
            twelfth body, and the sniper execute deletes the last 600 HP of
            the boss for free.
2026-09-09  Economy measured and repriced. A 15-wave run earns 6580 gold; the
            most all four weapons could absorb under the old flat tier curve
            was 6870, so a run could buy 96% of everything the game sells and

            across twelve paths cannot drift out of step. Also fixes pacing
            for free: 55% of a run's gold arrives in the last five waves, and
            the expensive tiers are now what that money is for.
2026-09-09  Mod cores deleted - all five, plus ModCoreType, their prices, the

            stacking between mods and upgrade trees. Double tap removed from
            the Gunslinger T2 as well. Fixed while in there: the HUD never
            showed an infinite reserve, because it only checked the weapon
            definition and not the resolved upgrade stat; and the shop's
            deployable buttons overlapped the ammo and barricade rows by 21px,
            a layout bug that predated all of this.
2026-09-09  Decision: three upgrade paths on all four weapons, not one. Sixty
            tiers total. Taken with the content cost understood, on the basis
            that the economy rework is what makes any of them a choice.
2026-09-09  Gunslinger path live. T1 guaranteed crit on the first shot after
            every reload; T2 25% crit and double tap; T3 fan the hammer, hold
            to fire at 600 RPM with spread bleeding 1.2 to 9 degrees and
            recovering on release, while a click stays an accurate double tap;
            T4 dual pistols, 45 damage, infinite reserve; T5 an ultimate at 30
            pistol kills - flourish reload, then the guns auto-aim while the
            player spins, 80% crits until the magazine runs dry.
            Two things checked rather than assumed: reload-spamming for the
            free crit is worse DPS than simply shooting, at every tier; and
            the guaranteed crit only arms on a reload that actually loaded
            rounds, so a dry reserve cannot hand one out.
            NOT PLAYED YET. Numbers most likely to need tuning are the 0.2s
            hold threshold that separates a tap from a fan, and the ultimate's
            duration - 30 rounds at 900 RPM is 2.0 seconds, which may be short
            for something that costs 30 kills.

KNOWN DEBT IN THE CURRENT BUILD
===============================================================================

1. ARENA SCENE IS GENERATED.
   ArenaBuilder overwrites Arena.unity wholesale. Retire it the moment
   hand-authoring starts - now Phase 3, not Phase 2 - or it will silently
   destroy level design work. Keeping it alive through content production is
   deliberate: it wires every new enemy, weapon and arena automatically.

2. INPUT IS POLLED DIRECTLY.
   InputReader reads devices rather than action maps. Commercial release needs
   full rebinding. Migrate to Input Actions in Phase 3 with the UI pass.

3. HUD USES LEGACY uGUI TEXT.
   Chosen to avoid the TextMeshPro import prompt on first run.
   Migrate in the Phase 3 UI pass.

4. NO SAVE OR SETTINGS PERSISTENCE.
   Needed for Phase 2 meta progression, and for making the endless-mode unlock
   persist. Expensive to retrofit, and it now arrives sooner than planned
   because content moved earlier.

5. NO ASSEMBLY DEFINITIONS. - DEFERRED, deliberately.
   Everything compiles into Assembly-CSharp. Reviewed 2026-09-08: 31 scripts
   do not cost real minutes yet, and asmdefs carry their own setup risk around
   editor and package references. Revisit when a compile is actually annoying.

6. ZOMBIE STEERING IS O(n^2), NOW WITH A PER-FRAME SPHERECAST ON TOP.
   ZombieAI.Separation walks every other live zombie each frame
   (ZombieAI.cs:210). Barricade sensing then adds a SphereCastNonAlloc per
   zombie per frame (ZombieAI.cs:141). At 60 agents that is ~3,600 distance
   checks plus 60 casts every frame; fine today, and the first thing to break
   when waves get dense.
   NOTE: this entry was briefly overwritten by the barricade-pathing note and
   marked resolved. It was not resolved - it got worse. Phase 4 references it
   for the spatial hash, so keep it at number 6.
   Fix: spatial hash or grid buckets for separation, and cache the barricade
   cast to every few frames rather than every frame.
   UNCHANGED by the flow field (2026-09-09). The field replaced the chase
   direction only; separation still walks every pair and the barricade cast
   still runs per zombie per frame. It did not get worse either - a field
   lookup is cheaper than the normalize it replaced.
   DEFERRED, deliberately. Reviewed 2026-09-08: maxAliveAtOnce is 60, so this
   is ~3,600 distance checks and 60 casts per frame - trivial for a modern
   CPU. A spatial hash now is premature optimisation. Revisit in Phase 2 when
   content production raises horde counts - that phase moved earlier, so this
   arrives sooner than originally scheduled.

7. SCENE SINGLETONS FAIL SILENTLY. - RESOLVED 2026-09-08.
   SystemsCheck runs in Start, after every Awake has assigned its instance,
   and reports any missing singleton as one Console error naming exactly what
   is absent and how to fix it. The null-conditional call sites stay - they
   are correct - but the whole class of failure is now loud instead of silent.
   Original entry follows.
   ---
   Reached through null-conditional calls, so one missing from the scene
   simply does nothing - no error, no warning. Now 27 call sites:
   ArmoryManager 10, SfxPlayer 9, CameraShake 4, ImpactEffects 2, TracerPool 1,
   HitStop 1. Every new system adopted the pattern instead of the pattern
   being fixed. Has already cost several debugging round trips.
   Fix: startup validation on each singleton, and extend the builder's
   Validate step to assert every singleton, clip and prefab landed.

8. EVERY NEW SCENE COMPONENT NEEDS A BUILDER RE-RUN.
   Adding a component in code does nothing until ArenaBuilder is run again.
   Easy to forget, and the symptom is silent (see item 7). Now mitigated by
   SystemsCheck, and goes away entirely when the builder retires in Phase 3.

9. HIT TEST IS A RAY, NOT A SPHERECAST. - DEFERRED, deliberately.
   Reviewed 2026-09-08: switching to a spherecast would subtly widen every
   shot, changing hit feel that has now been validated through two gates. Not
   worth destabilising for a case that cannot currently occur. Fix it when an
   enemy actually closes inside the player's centre, not before.
   Shots are correct now that the ray starts at the player's centre, but an
   enemy that closes inside that centre would still be missed. Cannot happen
   at current values - zombies stop at 1.6 units - but a fast archetype in
   Phase 1 could. Switch to SphereCast when that enemy exists.

10. VFX SIZES ARE TUNED TO ONE CAMERA DISTANCE.
   Sparks and shell casings are sized in world units for a camera 22.8 units
   out (~45 px per unit). Any change to camera height or FOV silently changes
   how readable they are. Revisit if the camera framing moves in Phase 2.
   The light art pass is exactly when that would happen.

11. THE BUILDER WILL NOT UPDATE EXISTING WEAPON ASSETS.
   LoadOrCreateWeapon only creates what is missing, deliberately, so hand
   tuning survives a rebuild. The flip side is that changing a default in
   ArenaBuilder does nothing to assets that already exist - they have to be
   edited in the inspector or deleted and regenerated. Expect this every time
   a weapon default changes.

12. WEAPON MODS ARE HARDCODED BY SLOT INDEX. - RESOLVED 2026-09-08.
   WeaponDefinition now carries WeaponTags (Sidearm / Shotgun / Rifle /
   Precision) plus its own Overclocked response values, and
   ArmoryManager.ModAppliesTo owns the mod-to-tag rules. Weapon.cs has no
   slot-index branching left; slotIndex survives only for reserve ammo
   lookup, which is legitimately positional. Reordering slots or adding a
   fifth weapon can no longer mis-assign a mod.
   Original entry follows.
   ---
   Weapon.cs branches on slotIndex == 0, isShotgun = slotIndex == 1, and
   slotIndex == 2 || slotIndex == 3. Reordering the loadout silently
   reassigns every mod to the wrong gun, and a fifth weapon means editing
   Weapon.cs. This directly undoes the point of moving weapons into
   ScriptableObjects one commit earlier.
   Fix: mods declare what they apply to, or WeaponDefinition carries tags
   (shotgun / precision / sidearm) the mods match against.

13. ARMORY PRICES ARE COMPILE-TIME CONSTANTS. - RESOLVED 2026-09-08.
   Costs live in an ArmoryPrices ScriptableObject, created once and then left
   alone on the same create-if-missing contract as the weapon definitions, so
   tuning survives a rebuild. ArmoryManager keeps static passthrough
   properties, so all ~20 UI call sites are unchanged.
   Original entry follows.
   ---
   ArmoryManager holds every cost as const int, so balancing the economy is a
   recompile rather than an edit. Painful once run structure is fixed and the
   economy actually needs tuning against it.
   Fix: move costs into a ScriptableObject alongside the weapon definitions.

15. MOD CORES ARE AN ENUM WITH HARDCODED BRANCHES. -- RESOLVED 2026-09-09.
   ModCoreType was an enum with every effect a branch in Weapon.cs, and it
   blocked the upgrades task: 60 upgrades would have meant 60 branches in one
   file. Resolved by DELETION rather than by the planned migration into
   ScriptableObjects - upgrade trees already did everything mods did, and
   keeping both meant two systems making a weapon stronger with neither aware
   of the other and untested stacking between them.
   Worth recording that deleting was cheaper than migrating and only became
   the obvious answer once the replacement existed. The register had assumed
   a rework for weeks.

16. WEAPON LOADOUT IS FIXED AT FOUR SLOTS. -- RESOLVED 2026-09-09.
   Split into a catalogue (everything sellable) and a carried array (what the
   run holds), so a slot is live simply by holding something rather than by a
   parallel unlocked[] flag. Carry capacity is 10 on the number row.
   It was filed as "a design choice rather than a defect", and that was right:
   it did not become answerable until the direction settled on one path per
   weapon, at which point the answer was obvious. Some register items are
   waiting on a decision, not on effort.

17. UPGRADE BEHAVIOUR FLAGS ARE A FLAT, GROWING VOCABULARY.
   UpgradeTier carries around 30 fields now - dualWield, fanFireRate,
   critChance, focusBonusPerHit, executeThreshold and so on - each read by an
   if in Weapon.cs. New tiers and whole new paths are still pure data, which
   was the point. But a new KIND of effect costs a field, a WeaponStats
   member, a line in UpgradeManager.Apply and a branch in the firing path.
   Four authored paths in, there is a useful distinction the raw count hides:
   of the seven fields the shotgun/rifle/sniper paths needed, THREE were plain
   stat overrides that should have existed from the start (pelletCount,
   spread, penetrationFalloff) and only Focus was a genuinely new mechanic.
   The abstraction to design is narrower than 30 fields suggests - most of the
   growth is stats the resolver simply did not cover yet.
   Still deliberately unfixed. Revisit after the firing-mode rework (debt 19),
   which will add the next real batch of mechanics and show whether the
   vocabulary or the firing path is the thing that actually needs restructuring.

18. GAMEPAD CANNOT REACH WEAPON SLOTS 5-10.
   The number row maps all ten; the d-pad has four directions and a pad has no
   tenth face button. Gamepad players can select the first four weapons only.
   Fix: bind cycling (shoulder buttons) rather than direct selection, which
   also wants the HUD to show the carried list rather than just the current
   weapon. Not urgent while the game is keyboard-first in development, but it
   is a real parity gap and it grows as weapons are added.

19. WEAPON.CS IS HITSCAN ONLY. -- RESOLVED 2026-09-09.
   Delivery is now a WeaponDelivery ScriptableObject on the definition, with
   Hitscan, Cone, Chain and Projectile implementations. A weapon that leaves
   the field empty falls back to hitscan, so the first four needed no assets.
   Worth recording that this was called correctly in advance: it was filed as
   shared infrastructure to build once rather than six times, and building it
   first meant the abstraction was designed against four real weapon shapes
   instead of one. Compare debt 17, which is still unfixed for the opposite
   reason - there were never enough examples to generalise from.

20. PROJECTILE KILLS DO NOT ROUTE THROUGH WEAPON.ONKILL.
   A projectile carries its damage rather than asking the weapon at impact,
   because by the time it lands the player may have swapped weapons, bought a
   tier or died - the shot has to be worth what it was worth when it was
   fired. The consequence is that kills it scores charge no ultimate and
   refund no reserve.
   Harmless for the Grenade Launcher and Nail Gun as designed, and NOT worth
   fixing speculatively. It becomes real the moment a projectile weapon wants
   an ultimate or a kills-refund tier, and the fix then is for the projectile
   to carry a callback to the weapon that fired it, guarded against that
   weapon having been swapped or destroyed.

22. THE FLAMETHROWER HAS NO SOUND.
   It fires ten times a second, so the shared gunshot clip machine-guns
   through the voice pool and reads as a stutter rather than a flame. Its
   fireClip and impactClip are deliberately null, which makes it silent.
   Fix: a looping sample with a proper loop point, started on first fire and
   faded out on release - which means SfxPlayer needs a concept of a held
   loop, not just one-shots. Any continuous weapon will want the same, so do
   it once. It WILL feel wrong to play before then; that is this entry, not a
   bug.

21. A CONDITIONAL COMMENT IS NOT A REMINDER.
   ZombieAI's own class comment said "the arena is open... swap in a
   NavMeshAgent if the map ever gains real obstacles". The arena gained
   fourteen cover blocks when it was enlarged on 2026-09-08, and nothing
   revisited the steering. The bug shipped into every play-test for a day
   before it was reported, and the code had described the exact precondition
   for its own failure the whole time.
   The lesson is not "write better comments" - that comment was excellent. It
   is that an assumption with an expiry condition has no owner unless it is in
   this file. When a comment says "revisit X if Y", Y belongs in the register
   or in the task that would cause it.

14. NEVER HAND-EDIT ASSET YAML FOR FIELDS THAT ARE NOT COMPILED YET.
   Learned the hard way 2026-09-08. Weapon tags were written straight into the
   .asset files while Unity was still compiling the WeaponDefinition change,
   so on reimport the keys were unknown and Unity silently discarded all
   twelve of them. Four of the five mods went dead - they check tags that were
   suddenly None - and nothing reported it, because the drum mags mod applies
   unconditionally and so still appeared to work.
   Rule: let Unity compile the field first, then write the value, then verify
   it survived a reimport. For anything larger than a few keys, use an editor
   script with SerializedObject instead of touching YAML - that path cannot
   write a field the assembly does not have.
